# 복잡성·과도한 제한 검토 — 2026-10-05

실기기 준비 검토와 수정 `97834af`를 main에 병합·push한 뒤, 최근 EFS/IMS/카페 보강을 반대 관점에서 검토했다. 사례의 희소성보다 실제 실패 영향, 근거의 범위, 사용자에게 강제되는 행동, 정상 경로를 막는지를 기준으로 삼았다.

## 정리한 부분

`data/omd.ts`의 SKT/KT SIM 위치 설명은 물리 USIM 등록 방식인데 카드가 eSIM 코드까지 포함해 모든 사용자에게 슬롯 이동을 요구하는 것처럼 보였다. [카페 원문](https://cafe.naver.com/x1smart/617140)은 물리 USIM의 슬롯 방식과 eSIM 상담 절차를 구분한다. 해당 범위를 명시하고 eSIM은 고객센터 안내를 따르도록 바꿨다. KT 옛 코드가 새 코드로 바뀌었다는 출처 없는 역사 설명도 기본 화면에서 제거했다. 기존 등록 코드·조건·출처는 유지하며 새로운 조건·확인창·상태·테스트는 추가하지 않았다.

## 남은 단순화 여지

Wizard는 여러 엔진의 흐름을 조정하므로 여전히 큰 파일이다. 순수 계획/판정/통신/저널은 분리했고 엔진 호출은 공통 dispatch·재연결·로그 함수로 묶었다. 추가 분리는 엔진 하나를 실제 검증한 뒤 동작을 보존하며 진행하는 편이 낫다. 지금 규모만을 이유로 실행 전체를 재작성하지 않는다.

OMD의 대안 코드와 자세한 IMS 기술명은 필요 시 펼치는 안내로 옮길 수 있지만 실행 경로나 필수 절차를 늘리고 있지는 않다. 이번에는 기존 화면 구조를 재설계하지 않고 근거/범위가 과했던 문구만 줄였다. 희귀 SIM 제조사 손상 가설·개별 로밍/밴드 사례는 런타임 예외로 넣지 않았다. 10 시리즈 전용 기능도 추가하지 않았다.

판단: 기능 자체보다 **지원 범위와 안내 문구를 보편적인 규칙처럼 말하는 것**이 더 큰 과잉 위험이었다. 그 부분을 정리했다. 남은 제한은 제거로 해결할 수 있는 가짜 위험 경고와 실제 미구현 기능을 구분해 관리해야 한다. 실기기 준비 상태의 범위는 [readiness-review-20261005.md](readiness-review-20261005.md)와 동일하다.

검증: 문자열·안내 문서만 바뀌었으므로 새 테스트는 추가하지 않았다. 직전 동작 변경의 97개 프런트·211개 Rust/8 제외·엄격 clippy 검증을 유지한다. 문구 수정 `2e6acac` 소스로 정적 프로덕션 빌드·기본 기능 release·NSIS 생성에 성공했다. 설치 파일은 3,432,720 B, SHA-256 `f8b9e5c4706acb0050177d8fd80b09729592a0e16987a69f99800b011df54edd`이다. 실행·설치·실기기 테스트 없이 기본 모든 쓰기 기능 꺼짐을 유지했다.
