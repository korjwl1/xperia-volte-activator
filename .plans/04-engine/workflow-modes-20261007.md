# 시작 경로 분리 — 자동 진행 / 수동 진행 / 업데이트

status: draft

작성일: 2026-10-07. 사용자 요청에 따른 구현 전 계획이다. 이번 작업은 이 문서만 작성한다.

갱신일: 2026-10-08. 업데이트 안내·백업 선택, 데이터 유지의 한계, 새 버전 부트 이미지 사전 패치와 후속 기록 정책을 추가했다. 화면/엔진 구현은 아직 하지 않는다.

## 1. 확정 요구사항

- 첫 화면에서 [시작하기]를 누르면 작업 종류 선택 페이지를 먼저 표시한다.
- 작업 종류는 **자동 진행 | 수동 진행 | 업데이트** 순서로 한 행에 배치한다.
- 업데이트는 현재 연결된 기기에서 VoLTE가 인식될 때만 선택할 수 있다.
- USIM 선택 페이지의 [언락만 진행하기] / [리락만 진행하기]를 제거하고 수동 진행 화면으로 옮긴다.
- 자동 진행은 기존 통합 작업의 내용과 조건별 생략 규칙을 계승한다. 백업이 끝나면 사용자가 다음 과정을 직접 시작한다. 그 외 단계 완료 후에는 자동으로 이어간다.
- 수동 진행은 작업 카드 그리드를 제공한다. 작업을 고르면 필요한 입력·준비 후 해당 작업만 실행한다. 기기 조건이 맞지 않는 작업은 비활성화한다.
- 업데이트는 기존 VoLTE 패치를 보존하는 전용 경로로 분리한다. 통신사 선택이 남아 있다는 이유로 재패치를 실행하지 않는다.
- 업데이트도 전용 안내·동의를 거치고 자동 진행과 같은 백업 선택 화면을 제공한다. 선택한 백업 완료 후 사용자가 [다음 과정 진행]을 누르기 전에는 펌웨어를 기록하지 않는다.
- 업데이트는 현재 부트로더 잠금 상태를 유지한다. 기존 Magisk 루팅 유지 선택 시 새 버전 이미지를 업데이트 전에 패치하고, Newflasher 순정 기록 후 별도 fastboot 계열 단계에서 적용한다.

## 2. 현재 코드와 변경 지점

| 현재 상태 | 필요한 변경 |
|---|---|
| `startSession()`이 `device → warning`으로 이동 | `device → mode-select`로 변경하고 선택 이후 분기 |
| `VolteConfigView`가 SIM·펌웨어·부트로더 단독 작업을 함께 제공 | 부트로더 단독 카드 제거, 업데이트 전용 화면 분리 |
| `buildPlan()`이 SIM 통신사 선택 여부로 패치와 업데이트 정책을 결정 | 명시적인 작업 종류를 실행 계획의 입력으로 추가 |
| `stepDone()`이 현재 모든 단계 완료 후 `awaitingNext`로 대기 | 자동 전환 정책과 백업 완료 대기를 구분 |
| `bootloaderOnly`와 `backupOnly`가 특수 경로로 존재 | 수동 작업 계획으로 통합하되 기존 기록의 호환성 유지 |
| 복구가 초기화 포함 계획에서만 만들어짐 | 수동 복구는 독립 계획으로 생성 |
| 실제 펌웨어 취득은 `boot/init_boot` 부분 다운로드 | 업데이트용 전체 펌웨어 다운로드·스테이징·기록 엔진 별도 구현 |
| `liveStepEnabled("fw-flash")`는 false, 실전 업데이트 계획은 차단 | 엔진 구현·검증 전까지 차단 유지. 화면 분리로 실제 업데이트가 구현됐다고 표시하지 않음 |

실행 러너와 백엔드를 복제하지 않는다. 자동·수동·업데이트 모두 같은 준비·실행·기록·오류 처리 코드를 사용하고, 계획 생성과 완료 후 이동 정책을 분리한다.

## 3. 화면 흐름과 배치

```text
기기 감지 → [시작하기] → 작업 종류 선택
                         ├─ 자동 진행 → 기존 안내·동의 → USIM/기존 옵션 → 계획 확인 → 실행 → 결과
                         ├─ 수동 진행 → 작업 그리드 → 작업별 안내·입력 → 계획 확인 → 실행 → 결과
                         └─ 업데이트 → 업데이트 안내·동의 → 대상 펌웨어·루팅 정책 → 백업 선택 → 계획 확인 → 실행 → 결과
```

작업 종류 선택 페이지:

```text
선택한 기기 / 현재 상태

┌────────────────┐ ┌────────────────┐ ┌────────────────┐
│ 1. 자동 진행   │ │ 2. 수동 진행   │ │ 3. 업데이트   │
│ 기존 통합 절차 │ │ 필요한 작업만  │ │ 기존 패치 유지 │
└────────────────┘ └────────────────┘ └────────────────┘

[이전: 기기 화면]
```

- 기본 창과 최소 지원 해상도에서 3열을 유지한다. 카드 크기·높이를 같게 하고 순서는 고정한다.
- 카드 선택은 설정 화면으로 진입하는 동작이다. 누르는 즉시 기기에 쓰지는 않는다.
- 업데이트 비활성 이유는 카드 안에 표시한다. 색상뿐 아니라 텍스트·아이콘·접근성 상태로 구분한다.
- 내부 콘텐츠 pane만 스크롤한다. 헤더·액션 바는 고정하며 시스템 테마, MD3 토큰, lucide 아이콘을 사용한다.
- 종류 선택/수동 작업 목록에는 기존 패치용 1~4단계 사이드바를 강제로 노출하지 않는다. 선택 이후 작업에 맞는 단계명을 표시한다.
- [이전]으로 이동하면 같은 기기의 입력은 해당 경로별로 보존한다. 경로 전환 시 실행 계획·위험 동의·검증 결과를 재생성하며 다른 경로의 SIM·펌웨어 선택이 작업을 추가하지 못하게 한다.
- 다른 기기를 고르거나 [처음으로]를 누르면 작업 종류, 수동 작업, 백업 뒤 승인, 펌웨어·이미지 검증을 초기화한다.

## 4. 업데이트 진입 조건

사용자의 “VoLTE가 인식되는 폰”은 첫 화면의 VoLTE 활성 표시와 같은 `cellularReady(sim)` 판정을 사용한다. EFS 파일 존재, 선택한 통신사, `persist.*` 속성, 과거 완료 기록으로 활성화하지 않는다.

이 계획에서는 **인식된 SIM 중 하나 이상이 셀룰러 IMS 음성 등록 상태일 때** 기기 단위 업데이트 카드를 활성화한다. 두 SIM 모두 활성 상태여야 한다는 조건은 추가하지 않는다. 업데이트 전 활성 슬롯을 기록하고 완료 후 같은 슬롯을 재확인한다.

| 상태 | 업데이트 선택 |
|---|---|
| 같은 기기, Android/ADB 승인 상태, SIM 하나 이상 `cellularReady=true` | 활성 |
| IMS 미등록·등록 중·음성 불가, SIM 없음 | 비활성 |
| Wi-Fi 통화만 등록 / 다른 SIM 경유 등록 | 비활성 |
| 조회 실패·미지원 출력·접속 방식 미확인·연결 해제 | 비활성 + 사유/재조회 |

- 종류 선택 화면에서도 기기 상태를 갱신한다. 이전 성공값만 계속 사용하지 않는다.
- 카드 클릭과 실제 플래시 시작 전 같은 기기·현재 IMS 상태를 다시 검사한다. 늦게 도착한 다른 기기의 조회 결과는 무시한다.
- 플래시 모드에 진입하면 IMS를 조회할 수 없으므로, 검증된 진입 전 스냅샷과 동일 기기 식별로 이어간다. 기록 중 IMS 불가를 작업 중단 조건으로 사용하지 않는다.
- VoLTE 조건과 실행 엔진 준비 상태는 분리한다. 조건을 만족해 설정에 진입할 수 있어도 엔진이 미구현이면 실전 [실행]을 차단하고 사유를 표시한다.

## 5. 자동 진행의 실행 정책

### 기존 내용 유지

현재 통합 계획의 준비, 백업, 필요한 언락·초기 설정, 루팅, EFS 적용·검증, VoLTE 설정, 선택한 언루팅·리락·복구, 최종 확인을 재사용한다. 이미 언락된 기기에 언락을 추가하거나 후처리 선택을 바꾸지 않는다. 기존 통합 경로의 펌웨어 동시 업데이트 선택은 우선 유지하되, 3번 업데이트 전용 경로와 별도 정책으로 생성한다.

### 백업 완료 후 한 번 대기

- 백업 산출물의 기존 완결 검사, 누락 안내, 임시 파일 처리까지 끝난 뒤 완료 처리한다.
- 후속 단계가 있으면 자동 진행을 멈추고 백업 결과·저장 위치·누락 상태·다음 작업을 표시한다.
- [다음 과정 진행]을 사용자가 눌렀을 때만 이어간다. 연결 복귀·타이머·화면 이동·재시작으로 자동 승인하지 않는다.
- 백업이 없으면 이 대기를 만들지 않는다. 백업이 마지막 작업이면 결과 화면으로 끝낸다.
- 불완전 백업은 기존 누락/불완전 백업 처리 정책을 유지한다. 단순히 [다음]으로 미완결 상태를 성공 처리하지 않는다.
- 사용자 재실행으로 새 백업 결과가 만들어지면 이전 승인은 무효다. 추후 여러 백업 단계가 생겨도 각 백업 완료 뒤 동일하게 대기한다.

### 나머지 완료 후 자동 전환

- 성공한 내부 단계마다 [다음]을 요구하는 현재 동작을 없앤다. 다음 단계를 순서대로 실행한다.
- `stepDone()`에서 즉시 다음 기기 I/O를 호출하지 않는다. 현재 엔진의 `finally`, 이벤트 구독 정리, 작업 잠금 반환이 끝난 후 다음 단계 하나만 시작한다. `busy`·`dangerBusy`와 실행 세대 검사를 사용한다.
- 사용자 중단·오류·미충족 조건·실제 수동 입력 대기는 자동으로 넘기지 않는다.
- USB 모드·재연결·루트 권한처럼 자동 판독 가능한 조건은 충족 시 자동 진행한다. 초기 설정, OEM 설정 변경, 언락 코드 입력, 폰 권한 승인, 문자 내보내기/가져오기, 실제 발신·수신 확인은 사람이 해야 할 동작으로 남는다.
- 위험 작업은 실행 계획 확인에서 대상 기기·초기화·기록 내용을 구체적으로 동의받고 백엔드 확인 조건을 유지한다. 완료 때마다 동일 동의를 반복하는 일반 [다음] 버튼은 제거한다. 별도 실기기 테스트 세션의 실행 승인 조건은 이 문서로 해제하지 않는다.
- 자동 연결/모드 대기 중 PC 보호를 유지하며, 백업 뒤 사용자 대기·중단·오류·완료 시 해제한다. 기록 중 I/O가 남아 있으면 기존 해제 지연 규칙을 따른다.

## 6. 수동 진행 — 작업 그리드

기본 3열 그리드. 사용자가 요청한 7개 작업에 **통신 확인**을 추가한다. 기존 패치를 바꾸지 않고 현재 상태를 확인하거나 작업 결과를 다시 확인할 수 있기 때문이다.

```text
백업          | 복구          | 언락
리락          | 루팅          | 언루팅
VoLTE 패치    | 통신 확인     |
```

업데이트는 첫 선택 페이지의 3번에 있으므로 중복 카드로 넣지 않는다. 별도 엔진이 없는 “최적화”, 일반 초기화, 국가 펌웨어 변경, PDC, 패치 제거는 이번 작업에 추가하지 않는다.

### 작업별 조건과 실행 범위

공통: 선택한 기기가 연결되고 지원 상태가 확인돼야 한다. 조회 불가를 충족으로 취급하지 않는다. 준비 화면 진입 가능 여부와 실제 [실행] 가능 여부를 나눈다. 이미지·백업 폴더를 아직 고르지 않았다는 이유로 카드 자체를 영구 비활성화하지 않는다.

| 작업 | 카드 선택 조건 | 준비/실행 범위 | 완료 후 |
|---|---|---|---|
| 백업 | Android, ADB 승인 | 항목·저장 위치·용량 확인 → 기존 백업/문자 내보내기/완결 검사. 루팅은 필요 항목에 대해서만 확인하며 비루팅 백업 가능 항목은 허용 | 백업 결과. 다른 작업 자동 실행 없음 |
| 복구 | Android, ADB 승인 | 기존 백업 폴더·manifest·해시·원본 기기·항목 검증 → 현재 기기에 덮어쓰는 항목 확인 → 복구·수동 가져오기. 새 백업이나 언락을 강제 추가하지 않음 | 복구 결과 |
| 언락 | 부트로더 locked, 지원 기종/언락 가능 여부에 명시적 불가 없음 | OEM 조건·코드·백업 여부·초기화 안내 → bootloader에서 같은 기기 재확인 → 언락·OS 복귀. 루팅·패치·리락을 추가하지 않음 | 초기 설정/재연결에 필요한 안내 후 언락 결과 |
| 리락 | 부트로더 unlocked, 지원 기종 | 순정 이미지 준비 → 현재 펌웨어/출처 확인 → 양 슬롯 순정 복원 → 기존 리락 게이트 → 리락·초기화·OS 복귀. 루트 미감지만으로 순정이라고 가정하지 않음 | 기본 설정/재연결 안내 후 리락 결과 |
| 루팅 | 부트로더 unlocked, rooted=false, 대상 파티션 지원 | 현재 설치 버전의 순정 이미지·Magisk 준비 → 패치·검증·기록·앱 설치·루트 확인. 언락/VoLTE 패치/리락 자동 추가 없음 | 루팅 결과 |
| 언루팅 | 부트로더 unlocked, rooted=true, 대상 파티션 지원 | 현재 버전 순정 이미지 확인 → 양 슬롯 복원·OS 복귀·루트 상태 확인·기존 Magisk 정리 안내. 리락 자동 추가 없음 | 언루팅 결과 |
| VoLTE 패치 | 부트로더 unlocked, rooted=true, 모델별 EFS 경로 지원 | USIM/통신사·프리셋 확인 → DIAG 준비·스냅샷·슬롯별 적용·리드백 → VoLTE 설정·재부팅·통신 확인. 언락/루팅/언루팅/리락을 추가하지 않음 | 패치·통신 결과 |
| 통신 확인 | Android, ADB 승인, SIM 인식 | 현재 SIM별 IMS·음성 상태 읽기 및 실제 통화 확인 UI. 필수 재부팅/권한 상승/기록 없이 조회하며 재부팅 확인은 사용자 선택 | 통신 상태 결과 |

- 언락: 이미 unlocked면 비활성. 리락/루팅/언루팅/패치: locked면 비활성. 잠금 상태 unknown이면 관련 카드 비활성이다.
- 루팅 상태 unknown이면 루팅/언루팅/패치는 재조회 안내를 표시한다. VoLTE가 이미 활성이라고 재패치 카드를 금지하지는 않는다.
- OEM 설정이 꺼져 있으나 사용자가 준비 화면에서 켤 수 있는 경우는 준비 안내로 연결한다. 기기에서 언락 불가가 확인되면 비활성화한다.
- DIAG COM 미지정·드라이버 준비·루트 권한 승인은 패치 준비 화면에서 해결한다. 실제 실행은 연결 검증을 통과해야 한다.
- 리락 게이트 입력이 미준비면 준비로 진입한다. 준비 이후 출처 불일치·손상 이력·일부 슬롯 실패가 있으면 실행을 비활성화한다. 우회 버튼을 추가하지 않는다.
- 작업 카드 클릭 뒤 설정·계획 확인을 거쳐 실행한다. 한 작업 안의 준비·검증은 자동으로 이어가고, 선택한 작업이 끝나면 결과와 [수동 작업 목록으로]를 제공한다.
- 최근 코드의 EFS 판정 정책을 계승한다: 리드백 차이는 로그/결과에 남기고, 읽기 자체의 실패는 중단한다. 재부팅 후 IMS 및 실제 통화 결과와 구분한다. 이 변경으로 과거 전수 해시 일치 강제 정책을 되살리지 않는다.
- 수동 복구 결과에서 기존 백업을 바로 삭제하도록 기본 유도하지 않는다. 백업 삭제는 기존 명시적 삭제 확인 조건을 유지한다.

## 7. 업데이트 전용 계획

### 사용자 흐름

VoLTE 진입 확인 → 업데이트 안내·동의 → 사용 중인 모델·지역의 새 버전 및 루팅 정책 선택 → 자동 진행과 같은 백업 선택 → 계획 확인 → 펌웨어/이미지 준비·검사 → 선택한 백업 → 백업 뒤 [다음 과정 진행] → 선택한 새 버전 이미지 사전 패치·PC 보관 → Newflasher 순정 기록 → 조건에 맞는 루팅 이미지 후속 기록 → 부팅·버전/지문·루트 확인 → 업데이트 전 활성 슬롯의 VoLTE/통화 확인 → 결과.

### 안내와 백업 선택

- 업데이트 안내에서 데이터/VoLTE 보존을 목표로 하되 손실·부팅 실패 가능성은 남는다는 점, 제외한 modem/DSP는 최신화되지 않는다는 점, 판올림의 별도 검증 범위를 설명한다. “초기화 없음”을 무손실 보장으로 표시하지 않는다.
- `BackupSelectView`와 공통 백업 엔진을 재사용한다. 항목, 저장 위치, 필요/가용 공간, 권한에 따른 수집 가능 범위, 기존 백업 처리와 누락 안내를 자동 진행과 동일하게 제공한다. 별도 축소 백업을 만들지 않는다.
- 비루팅 기기에서도 읽을 수 있는 백업 항목을 제공한다. 보호된 앱 데이터를 백업하려고 이 경로에서 새 언락·루팅을 강제하지 않는다. 수집 불가 항목과 그 이유를 표시한다.
- 백업을 선택하면 §5의 완결 검사·누락 처리·완료 뒤 사용자 대기를 그대로 적용한다. [다음 과정 진행]은 확인한 백업 결과와 연결하고, 새 백업·기기 변경·재개 시 이전 승인을 자동 재사용하지 않는다.
- 백업 생략도 선택 가능하다. 계획 확인에서 중요한 데이터는 별도 백업이 필요하고 앱 전체 복원을 보장하지 않는다는 안내와 생략 선택을 표시한다. 이후 숨은 백업 단계나 백업 뒤 대기를 만들지 않는다.
- 정상적인 데이터 유지 업데이트 뒤에는 자동 복구/덮어쓰기를 실행하지 않는다. 오류 후에도 자동 초기화·리락·백업 삭제를 하지 않으며 백업 위치와 수동 복구 진입을 제공한다.

### 데이터 유지와 판올림 검증

- `userdata*.sin` 제외에 더해 고정 Newflasher 버전의 `keep userdata` 응답과 실제 건너뛴 파일을 검증한다. `update.xml`의 `NOERASE` 대상, metadata 등 암호화 관련 이미지, 파티션 재구성 영향을 검사한다. 필수 보존 목록·구조를 해석할 수 없거나 기록 대상에 보존 파일이 남으면 실행을 막는다.
- TA 파일 제외는 펌웨어 입력의 `.ta` 파일 정책이다. Newflasher 프로토콜 내부의 모든 TA 명령이 없어지는 것으로 표현하지 않는다.
- 모델·지역과 출발/목표 펌웨어·Android 버전 조합의 검증 상태를 기록한다. Android 14→15 같은 판올림에 모뎀 유지 전략이 적용된 외부 사례가 있어도 다른 기기의 성공으로 확대하지 않는다. 확인 불가 조합은 미검증으로 안내하고 배포용 실전 활성화는 기존 체크리스트 기준을 따른다.
- Hanabi의 Xperia 1 VI Android 15 글(2024-11-27)은 모뎀 제외·리락 기기 진행과 백업을 안내하고 Bluetooth 오디오 후속 문제를 별도로 다뤘다. 앱의 XQ-DQ44 판올림 실측은 아직 없다. 앨리자 가이드 댓글에는 업데이트 후 부팅 실패로 공장초기화를 선택한 사례가 있으며 원인은 확정되지 않았다.

### 업데이트 유지 정책

- 새 버전만 선택한다. 같은 버전이면 작업 없음, 다운그레이드/지역 변경/순정 복구는 이번 경로에 넣지 않는다.
- 플래시 정책은 `preserve-volte`로 고정한다. `modem*.sin`·`dsp*.sin`·모든 `.ta`(boot 하위 포함)·`userdata*.sin`을 제외하고 사용자 데이터 유지 옵션을 사용한다.
- 원본 펌웨어에서 파일을 지우지 않고 스테이징 허용 목록으로 제한한다. 경로 이탈·중복·예상 밖 이미지 및 정책 불일치를 실행 전에 거부한다.
- 패치가 남는 이유는 모뎀·DSP를 갱신하지 않기 때문이라고 안내한다. 해당 구성 요소의 새 수정·보안 패치까지 적용됐다고 표시하지 않는다. 버전 혼재와 기종별 호환성 검증이 필요하다.
- 언락·리락·EFS 재주입은 계획에 넣지 않는다. 기존 SIM 선택은 업데이트 이전/이후 확인할 슬롯 정보로만 쓰며 패치 대상 입력으로 해석하지 않는다.
- 이미 Magisk 루팅된 기기는 새 버전의 이미지로 루팅 유지 여부를 명확히 선택한다. 기본 제안은 기존 루팅 유지다. 비루팅은 기본 비루팅 유지이며 언락 상태 자체가 이미지 수정을 요구하지 않는다. 잠금/루팅 상태 unknown 또는 지원하지 않는 루팅 방식은 관련 유지 실행을 차단하고 확인을 안내한다.
- VoLTE 재패치가 필요한 사용자는 자동 또는 수동 패치를 선택한다. 업데이트 완료 후 IMS 실패를 이유로 언락·재패치를 자동 추가하지 않는다.
- 기종 상태를 확인하지 않고 슬롯 A를 일괄 강제 지정하지 않는다. 기록 성공, OS 복귀, 펌웨어 버전/지문, 통신 확인을 각각 판정한다.

### 부트로더·루팅 상태별 이미지 정책

| 현재 상태 / 선택 | 업데이트 전 준비 | Newflasher 이후 |
|---|---|---|
| locked / 비루팅 | 같은 모델·지역의 순정 펌웨어 검사. 수정 IMG 없음 | 잠금·비루팅 유지, OS/VoLTE 확인 |
| unlocked / 비루팅 / 기본 선택 | 순정 펌웨어 검사. 언락 유지를 위한 별도 패치 없음 | 잠금 전환 없이 비루팅 유지 |
| unlocked / Magisk 루팅 / 루팅 유지 | **목표 버전**의 순정 boot/init_boot를 같은 폰에서 패치하고 PC에 저장·출처/해시 검증 | 순정 기록 완료 후 준비한 IMG를 검증된 fastboot/fastbootd 경로로 기록, 부팅·uid=0 확인 |
| unlocked / 루팅 / 비루팅으로 업데이트 | 순정 펌웨어 검사. 루팅 이미지 기록 생략 | 순정 부트 기록 후 루트 없음 확인·Magisk 앱/모듈 정리 안내. 리락 생략 |
| unlocked / 비루팅 / 명시적 새 루팅 선택 | 지원 파티션·Magisk 준비와 별도 선택 내용 확인 후 목표 이미지 패치 | 준비한 IMG 기록·루트 확인. 언락 자동 추가 없음 |

- 신규 루팅 선택을 제공할 경우 이미 unlocked인 지원 기기에만 표시하며, 기본 선택으로 켜지 않는다. locked 기기의 업데이트를 위해 언락을 넣지 않는다. 선택 가능한 루팅 방식은 현재 구현된 Magisk 범위이며 KernelSU/ReSukiSU를 같은 엔진으로 처리한다고 표시하지 않는다.
- Magisk 패치 IMG를 `.sin`으로 이름 변경하거나 펌웨어 `.sin` 내부에 삽입하지 않는다. Newflasher는 Sony 서명을 포함한 SIN을 업로드하는 경로이며 일반 raw IMG를 같은 방식으로 기록하는 엔진이 아니다. 폰의 언락이 Sony SIN 서명을 생성해 주는 것은 아니다.
- 펌웨어 스테이징과 패치 IMG 보관 폴더를 분리한다. Newflasher에는 필요한 순정 boot/init_boot도 그대로 기록하고, 그 뒤 새 패치 IMG를 덮어쓴다. 이전 버전 패치 이미지를 재사용하거나 순정 부트를 제외해 구버전 루트를 남기는 전략은 사용하지 않는다.
- 사전 패치는 업데이트 전 **같은 폰**의 Android/ADB 환경에서 수행하고 PC 사본·해시를 확보한다. 이미지 패치 자체는 기존 root가 필수는 아니지만 수정 이미지 기록·부팅에는 unlocked 상태가 필요하다.
- 현재 `magisk_patch_with_events`는 이미지 지문을 현재 설치된 지문과 대조한다. 목표 버전 사전 패치는 기존 API를 그대로 호출하면 실패하므로 별도 준비 계약이 필요하다. 현재 지문 검사를 전역으로 완화하지 않고, 같은 기기·출발 지문·목표 펌웨어 출처·파티션·부모/패치 SHA-256을 묶은 업데이트 준비 증명을 도입한다.
- Newflasher 후 직접 fastboot로 넘어가 첫 OS 부팅 전에 IMG를 기록하는 경로는 **기종·버전별로 검증된 경우에만** 사용한다. 이때 같은 기기, 목표 순정 기록 완료와 준비 증명, 대상 모드/슬롯을 확인한다. 현재 ADB 지문 검사만으로 이 상태를 검증할 수 있다고 가정하지 않는다.
- 직접 연계가 미검증이면 순정 OS로 한 번 부팅해 같은 기기·목표 지문을 대조한 뒤 기존 기록 절차로 준비 IMG를 적용한다. 사전 패치는 어느 경로든 Newflasher 전에 완료한다. 현재 공통 기록 API의 fastbootd 요구와 boot 기종 미검증 범위를 지킨다.
- 잠금 상태는 업데이트 전후 동일하게 유지한다. vbmeta 검증 해제·암호화 옵션 변경을 루팅 유지의 기본 작업으로 추가하지 않는다. Magisk 버전/모듈의 목표 Android 호환성을 확인하고 모듈이 모두 유지됐다고 단정하지 않는다.
- 사전 준비 실패는 Newflasher 전에 중단한다. 순정 업데이트 성공 뒤 IMG 기록만 실패하면 “업데이트 완료 / 루팅 유지 실패”로 구분하고 준비 IMG·순정 IMG·진행 기록을 보존한다. 이전 펌웨어로 자동 다운그레이드하거나 재언락하지 않는다.

### 미구현 엔진 작업

1. 전체 펌웨어 취득/사용자 지정 폴더 입력, 모델·지역·목표 지문 검증, 디스크 공간·캐시 관리.
2. 펌웨어 구조·NOERASE/암호화 보존 검사와 플래시 허용 목록을 만드는 스테이징 엔진.
3. 목표 버전 이미지의 사전 패치 준비 계약·PC 보관·출처 증명, 기존 현재 지문 검사와의 분리.
4. 고정 버전 newflasher 실행 래퍼, 출력/프롬프트 식별, 사용자 데이터 유지 정책 확인, 종료/실패/연결 오류 처리.
5. 기록 완료 후 같은 기기·목표 순정 기록 증명과 필요 시 fastboot 계열 루팅 기록, OS 복귀·목표 지문·root/IMS 재확인.
6. 실행 capability·facade·로그/이벤트 계약·기록 저장 연결. 기존 부트 부분 다운로드 API를 전체 펌웨어 API로 가장하지 않는다.

기존 계약 문서의 `fw_prepare` / `newflasher_run`은 설계 계약이다. 구현 때 실제 시그니처·이벤트·취소 가능 범위를 확정하고 facade/Rust 등록을 함께 작성한다. 실행 중 취소는 임의 USB 강제 종료가 아닌 엔진이 보장하는 경계에서 처리한다.

## 8. 상태·계약·기록 설계

구현 시 이름 확정 예정인 추가 상태:

```ts
type WorkflowMode = "automatic" | "manual" | "update";
type ManualOperation = "backup" | "restore" | "unlock" | "relock"
  | "root" | "unroot" | "volte-patch" | "communication-check";
type UpdatePolicy = "preserve-volte" | "repatch";
type UpdateRootPolicy = "stock" | "preserve-magisk" | "install-magisk";
// 자동 흐름의 동시 업데이트는 repatch, 업데이트 전용은 preserve-volte.
// install-magisk는 이미 unlocked인 비루팅 기기의 명시적 선택에만 사용.
// continuation에는 백업 뒤 대기와 사용자 중단/재개 대기를 구분해 저장한다.
```

- 새 뷰: `ModeSelectView`, `ManualTasksView`, `UpdateConfigView`. 수동 설정은 기존 백업/부트 이미지/USIM/통신 UI를 작업에 맞게 재사용한다.
- 순수 도메인에서 작업별 availability(선택 가능·실행 가능·사유·준비 필요)와 계획을 생성한다. 카드와 실행 직전 검사가 같은 판단을 사용하고 백엔드도 기기 조건을 다시 확인한다.
- 실행 계획은 작업 종류·기기·옵션으로 명시적으로 생성한다. 기존 `bootloaderAction`은 새 입력에서 제거하고, 과거 journal 해석에만 필요한 호환 경로를 남긴다.
- 백업 뒤 대기는 실행 완료된 백업과 연결해 기록한다. 재개 시 manifest 재검증 후에도 사람이 누르기 전에는 다음 쓰기를 실행하지 않는다.
- 자동 전환 중 마지막 engine 정리/저장 완료 이전에 다른 쓰기가 시작되지 않도록 순차 실행을 보장한다. 중단·종료·기기 변경 후 도착한 이벤트가 다음 작업을 시작하지 못하게 한다.
- 기록에는 mode·manualOperation·updatePolicy·백업 뒤 대기·업데이트 이전 통신 스냅샷을 포함한다. 언락 코드·IMEI 등은 저장하지 않는다.
- 업데이트 기록에는 루팅 정책, 출발/목표 지문, 순정·패치 이미지 출처/해시, 사전 패치 완료, Newflasher 완료, 후속 슬롯별 기록과 최종 root 판정을 각각 저장한다. 중간 재개에서 순정 기록 완료를 루팅 유지 완료로 읽지 않는다.
- 기존 기록의 `awaitingNext`는 안전하게 수동 재개 대기로 읽는다. 새 자동 전환 정책을 적용해 미완료 쓰기를 자동 재생하지 않는다.
- mode 없는 기록은 `backupOnly`/`bootloaderAction`/기존 계획을 근거로 호환 경로를 정하고 사용자에게 작업 내용 확인 후 재개하게 한다. 추론이 모호한 기록은 원본 보존 후 새 계획 안내로 처리한다.
- 수동 복구의 명시적 사용자 선택은 자동 계획의 “초기화가 있을 때만 복구” 규칙과 분리한다.

### 버튼 → 계약 매핑

| 인터랙션 | 연결 |
|---|---|
| 시작하기 / 종류 선택 / 수동 목록으로 | 프론트 상태 전이, 기기 고정, 미완료 기록 확인 |
| 상태 다시 확인 / 통신 확인 | 기존 `api.deviceList` / `api.deviceStatus`, `cellularReady`, 통신 패널 |
| 백업·복구 준비/실행 | 기존 `backupPrepare`, `backupRun`, `backupManifestCheck`, `restoreRun`, 문자/연락처 계약 |
| 언락·리락 준비/실행 | 기존 `fastbootGetvar`, `fastbootUnlock`, `bootImageCheck`, `fastbootFlash`, `relockGateCheck`, `fastbootLock`, 재부팅/모드 감지 |
| 루팅·언루팅 | 기존 순정 이미지 취득·검사, Magisk 계약, fastboot 기록 및 root 확인 |
| VoLTE 패치 | 기존 `efsApi`·프리셋/DIAG 준비·스냅샷·적용·리드백·활성화·통신 확인 |

| 백업 뒤 다음 과정 진행 | 대기 상태 검증/승인 기록 후 공통 러너 재개. 버튼 자체는 직접 기기 I/O 호출 안 함 |

## 9. 구현 순서와 문서 동기화

1. 작업 종류/수동 작업/업데이트 정책 타입, 순수 availability와 계획 생성 분리. SIM 선택에서 경로를 추측하는 결합 제거.
2. 시작 종류 선택 3열 화면, 수동 작업 그리드, USIM 페이지의 단독 언락/리락 카드 제거, 셸·사이드바·뒤로 이동 연결.
3. 수동 백업·복구·언락·리락·루팅·언루팅·패치·통신 확인의 입력 화면과 기존 엔진 연결.
4. 완료 후 자동 전환과 백업 뒤 단일 대기, I/O 정리·중단·PC 보호·진행 기록 호환 구현.
5. 업데이트 전용 화면과 VoLTE 진입 조건, 전체 펌웨어 엔진 및 유지 정책 구현. 미구현 단계와 실전 단계를 섞은 실행은 계속 차단.
6. 오프라인 검증 후 실기기 확인 항목을 기존 `device-test-checklist.md`에 추가. 실기기 실행·플래그 활성화는 해당 검증 절차에서 진행.

## 10. 완료 기준과 검증 계획

- [ ] 시작하기 직후 자동/수동/업데이트가 순서대로 동일 행에 표시되고, USIM 화면에 단독 언락/리락 카드가 없다.
- [ ] VoLTE 활성 SIM 하나가 있는 듀얼 SIM은 업데이트 선택 가능. 미등록/조회 실패/Wi-Fi만 등록/연결 해제는 불가. 기기 교체·늦은 조회가 상태를 오염시키지 않는다.
- [ ] 자동 진행은 백업 완료 뒤만 일반 다음 버튼을 요구한다. 백업 없음/백업 마지막/복수 백업/불완전 백업도 정의된 동작을 따른다.
- [ ] 자동 전환이 엔진 종료 전에 시작되지 않고, 중단·오류·종료·재시작 후 쓰기가 자동 재생되지 않는다.
- [ ] 수동 각 작업에 무관한 패치/업데이트/언락/리락 단계가 추가되지 않는다. 리락에는 필요한 순정 복원·게이트가 포함된다.
- [ ] 수동 복구는 초기화 이력 없이도 검증된 백업을 명시적으로 선택해 실행할 수 있다. 덮어쓰기·다른 기기·손상 백업은 검증 정책을 따른다.
- [ ] 업데이트 계획은 남아 있는 통신사 선택과 무관하게 모뎀·DSP·TA·사용자 데이터를 제외하고 언락/리락/EFS 주입을 만들지 않는다.
- [ ] 업데이트 안내·백업 선택은 자동 흐름의 공통 UI/엔진을 사용한다. 백업 선택/생략/권한 부족·누락 처리·완료 뒤 승인·재개가 정의된 동작을 따른다. 업데이트 성공 뒤 자동 복구를 하지 않는다.
- [ ] NOERASE 및 암호화 관련 보존 검사가 해석 불가/보존 대상 기록을 차단한다. 판올림 안내가 다른 기종의 성공 사례를 우리 기기 실측으로 표시하지 않는다.
- [ ] locked 비루팅·unlocked 비루팅·기존 Magisk 유지·비루팅 전환·명시적 신규 루팅의 계획이 분리된다. 언락만으로 루팅 선택이 켜지지 않는다.
- [ ] 사전 패치는 같은 폰에서 목표 버전 원본을 사용하고 PC에 검증된 사본을 남긴 뒤 Newflasher로 진행한다. raw IMG/SIN 변조·구버전 패치 재사용은 거부한다.
- [ ] 목표 이미지 준비 계약이 기존 현재 지문 게이트를 전역 완화하지 않는다. 직접 fastboot 연계와 순정 OS 확인 후 연계, 순정 업데이트 성공/루팅 실패·재개 상태가 구분된다.
- [ ] 업데이트 미구현 엔진은 실전 실행을 막고 모의 성공으로 표시하지 않는다. 루팅 유지 여부는 선택한 정책대로만 적용된다.
- [ ] 기존 journal 호환과 백업 뒤 대기 복원이 작동하며 완료 화면에서 수동 목록/종류 선택으로 정확하게 돌아간다.
- [ ] 기본 쓰기 feature/REAL_STEPS, facade 경계, 기기 식별·펌웨어·리락 검증 조건이 유지된다.

구현 후 검증은 `pnpm.cmd check`와 기존 domain/store의 가짜 IPC 테스트를 중심으로 한다. 분기별 계획, 활성화 조건, 백업 뒤 대기·자동 전환 경쟁, 기존 기록 호환, 복구 원본 검증, 스테이징 허용 목록을 검증한다. 화면은 최소 해상도/기본 창, 밝은/어두운 테마, 키보드 탐색과 비활성 사유를 확인한다. 실제 USB/DIAG/펌웨어 기록은 문서 작성 단계에서 실행하지 않는다.
