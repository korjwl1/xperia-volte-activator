## 후속 점검의 상태 보존 규칙

- 원복 저장소는 `backup/sms_role.rs`, 저장 위치는 `<앱 데이터>/sms-role/<SHA-256(ro.serialno)>.json`이다. 파일에는 버전·기기 키·원래 문자 앱 패키지만 저장하며 원본 시리얼은 저장하지 않는다. 시리얼이 확인되지 않으면 역할 변경을 거부한다.
- 이미 sms-ie로 전환된 기기의 재시도는 기존 원복 기록을 유지한다. 원래부터 sms-ie가 기본 앱이면 마무리에서도 유지한다. 사용자가 다른 기본 앱을 선택한 경우 자동으로 덮어쓰지 않는다.
- 원복 실패, 명령 성공 뒤 실제 역할 불일치, 기록 손상/저장 실패는 모두 실패다. 성공 확인 전에는 원복 기록을 지우지 않는다. 기록이 없는 이전 버전의 중단 작업은 원래 앱을 추측하지 않고 설정에서 확인하도록 안내한다.
- 종료 저장 실패 시 화면으로 돌아와도 작업은 정지 상태다. [이어서] 또는 실패 단계 재시도로 다시 시작한다. 백엔드에서 이미 시작된 복원이 즉시 취소되는 것은 아니며, 기존 변이 작업이 남아 있으면 새 호출을 거부한다.

## 검증

- Rust 단위 테스트: 일반 실행만 사용. live_* 및 ignored 테스트는 실행하지 않음.
- 프런트엔드: 실제 Svelte store/domain을 Vite로 컴파일하고 IPC를 메모리 가짜로 주입.
- HTTP Range: localhost 가짜 서버로 정상/200 응답/잘못된 범위/짧거나 긴 본문 검사. Sony 서버 다운로드는 실행하지 않음.
- 경로/해시/복원: 임시 디렉터리·FakeADBDevice로 네 번째 파일 손상, 누락된 격리 파일, 매니페스트 밖 파일, 선택하지 않은 항목/이전 tar 버전, 원본 mtime, 취소·재개 등을 검사.
- 후속 점검: 영속 원복 기록/기기 교체/재연결/저장 실패/실제 역할 불일치/사용자 기본 앱 변경, 설정 읽기 오류·중복 키, 디스크 기록 크기 상한을 가짜 I/O로 검사. 격리 tar의 미선택 1MiB 본문을 읽으면 오류가 나는 입력으로 실제 seek 사용을 검사했다. 처리 시간 벤치마크는 하지 않았다.
- APK 세션 생성/확정의 출력이 Success여도 종료 코드가 실패인 경우, 실패 문구에 Success가 포함된 경우, 누락/빈 APK의 전송 차단·abandon 및 정리 실패 로그를 가짜 기기로 검사했다.
- `pnpm test`: 23개 통과. SvelteKit 생성 파일을 공유하므로 테스트 파일은 순차 실행한다.
- `cargo test --lib`, `cargo test --lib --all-features`: 각각 113개 통과, live_* 5개 제외.
- `pnpm check`: 오류 0·경고 0. `pnpm build`: 정적 프로덕션 빌드 통과.
- `cargo fmt --all -- --check`, `cargo clippy --lib --all-features -- -D warnings`: 통과.

## 이번에 실제 테스트하지 않은 부분

이전 main 문서의 2026-10-03 실측은 그때의 코드에 대한 기록이다. 아래 변경의 실기기 검증을 대신하지 않는다.

1. Sony USB 재연결·복수 장치·ADB 서버 공존, shell exit code/권한 오류의 실제 기기 출력.
2. 백업/복원 중 연결 해제·저장 공간 부족·취소·재시도, 대용량 파일/NTFS 링크·긴 경로의 실제 동작 및 처리 시간.
3. Android toybox tar 호환, 원본 mtime·격리 이름 복원, split APK 설치 실패 후 abandon, 연락처 가져오기.
4. SMS Import/Export 설치·권한·내보내기·가져오기, 기본 문자 앱 전환/원복 및 강제 종료 후 실제 재연결·기기 교체. 저장소 재조회와 가짜 역할 서비스는 검증했지만 실제 Android 역할 출력/전환 시간은 미실측. 실제 문자·MMS·통화 기록의 내용/개수는 가짜 I/O 테스트가 보증하지 않음.
5. Sony 서버/CDN의 Range 응답, 실제 SIN/ZIP64·현재 펌웨어 지문과 추출 이미지의 부팅 호환.
6. fastboot USB claim/전송·언락 후 초기화/재부팅·슬롯별 이미지 쓰기. 기존 fastboot 문서의 미검증 항목도 계속 적용.
7. 실제 Tauri 창 닫기/화면 이탈과 Windows 로그아웃·재시작 중 보호 적용·진행 기록 보존. 종료/재시작 실험은 하지 않음.

## 현재 남아 있는 한계

- 순정 부트 체인×슬롯 증거와 AVB 검증이 없으므로 실제 리락은 차단한다.
- REAL_STEPS 기본값은 모두 false, fastboot 쓰기는 Cargo fastboot-write 기능도 필요하다. 루팅·EFS·전체 펌웨어 기록 등 나머지 실행 단계는 아직 시뮬레이션이다.
- 질의 timeout은 하위 USB/HTTP I/O를 강제 취소하지 않는다. 살아 있는 스레드를 제한하며, 뒤늦은 응답은 화면에 적용하지 않는다. 단일 파일 전송/복원 도중 즉시 취소도 아직 보장하지 않는다.
- SMS 원복 기록은 기기별로 영속 저장하지만, 기록이 없는 이전 버전의 작업이나 앱 데이터 삭제/손상 이후의 원래 기본 앱은 복구할 수 없다. 강제 종료/정전 시 파일 시스템 내구성은 실험하지 않았다.
- 신규 덤프는 해시가 있지만 예전 artifact-only 덤프는 해시가 없다. 기존 파일 내용의 동일성을 사후에 증명할 수 없다.
- 백업 재개의 기기 대조는 기존 모델·마스킹 시리얼을 사용한다. 같은 접두사의 기기까지 암호학적으로 구분하지는 못한다.
- SHA-256은 백업 파일 손상을 검사하며 매니페스트의 진위를 인증하지 않는다. APK PK 헤더 확인도 서명 인증서 검증을 대체하지 않는다.
- Wizard는 화면·실행 상태 조정 역할을 함께 가진다. 순수 정책/공통 I/O는 분리했지만 모든 단계의 별도 실행 서비스 추출까지 완료한 구조는 아니다.

후속(사용자 승인): 실행 전 확인 모달·⚠ 툴팁·창 닫기 보호가 `stepHazard()` 하나로 루팅·언루팅·EFS 수정까지 다룬다. 기기 작업 중에는 [이어서]를 표시하지 않는다. `rooted`는 true/false/"unknown" — su가 안 보여도 부트로더 잠김이 확정될 때만 false. 백업 취소는 실행마다 만든 runId로 대상을 지정해, 시작 전 취소도 반영하고 이전 취소가 다음 실행에 남지 않는다. sms-ie 다운로드는 USB 연결을 잡지 않은 채 한다.

adb_client I/O 상한(후속, 사용자 승인): 원본은 USB 읽기 상한이 무한이고 서버 소켓에 상한이 없어 기기가 멈추면 실행권·USB 잠금이 앱 재시작까지 잡혔다. `src-tauri/vendor/adb_client`에 사본을 두고 `[patch.crates-io]`로 연결해 USB 유휴 읽기 300초·쓰기 30초, 서버 접속 5초·읽기/쓰기 300초 상한을 넣었다(exec/shell 양방향 읽기·wait-for·track-devices는 읽기 상한 해제). 변경 목록은 `vendor/adb_client/PATCHES.md`. 오류가 나면 `with_first_device`가 USB 연결을 버려 다음 호출이 다시 연결한다.

남은 위험(코드로 해결하지 않음): 프로브 시간 제한(30초 등)이 지나도 작업 스레드는 I/O 상한(최대 300초)까지 USB 잠금을 쥘 수 있다. 기기 측 `tar -xf -`가 stdin EOF를 기다리는지는 실기기 확인 필요. Magisk·sms-ie APK는 GitHub 자산 다이제스트와 서명 인증서 핀으로 검증한다(`apk_verify.rs`). 다만 핀은 서명의 암호 검증이 아니고, GitHub 릴리스 자체가 오염되면 다이제스트도 함께 바뀐다.
